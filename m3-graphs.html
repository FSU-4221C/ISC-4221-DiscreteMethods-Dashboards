    3.1.1 Euler's Königsberg bridge problem

    # Permalink to topic 3.1.1, Euler's Königsberg bridge problem
    • ● Slides
    • ● Tutorial
    • ✚ New for 2026

    Eighteenth-century Königsberg sat on both banks of the Pregel and on two islands, joined by seven bridges. The town's puzzle: is there a walk that crosses every bridge exactly once? Euler answered it in 1735, and the way he answered it is what created graph theory.

    His move was to throw almost everything away. The length of a bridge does not matter. The shape of an island does not matter. What matters is only which landmass connects to which, and how many times. Strip the map down to that and you get four points and seven links — the first graph.

    Bridge list behind figure 3.1.1

    The seven bridges of Königsberg as an edge list. Two pairs of landmasses are joined twice, which is what makes this a multigraph rather than a simple graph.
    Bridge Joins To
    1A (island)B
    2A (island)B
    3A (island)C
    4A (island)C
    5A (island)D
    6BD
    7CD

    Key idea

    The answer is no, and the reason has nothing to do with Königsberg. Every time you enter a landmass you must leave it again, so every landmass except your start and your finish needs an even number of bridges. All four of Königsberg's landmasses have an odd number. Topic 3.1.6 turns that observation into a rule you can check, and the demo there checks it for you.

    3.1.2 What is a graph?

    # Permalink to topic 3.1.2, What is a graph?
    • ● Slides
    • ▣ Lab 07
    • ● Tutorial

    A graph is a set of vertices, some of which are joined in pairs by edges. That is the whole definition. Everything else in this module is a consequence of it.

    Definition

    Graph
    A pair G = (V, E) where V is a set of vertices and E is a set of edges, each edge being a pair of vertices.
    Vertex
    One of the things being connected. The slides, the tutorial and the labs use vertex, node and point interchangeably; so does this page.
    Edge
    A connection between two vertices. Also called a link. Written as a set, {A, B}, when direction does not matter.

    The Königsberg graph written as a list of edges is exactly {{A,B}, {A,B}, {A,C}, {A,C}, {A,D}, {B,D}, {C,D}}. Notice what that list drops: the river, the distances, the shapes. A graph "allows us to drop unimportant information", and that is a feature — the same four points and seven links describe any system with that connection pattern.

    The running example for the next two groups is the graph the slides call SIMPLE: five nodes A to E, four edges, and one node with no edges at all.

    3.1.4 Graph taxonomy (directed, weighted, simple)

    # Permalink to topic 3.1.4, Graph taxonomy (directed, weighted, simple)

    Four questions about what an edge is allowed to be. Each answer names a class of graph, and the class you are in decides which algorithms are legal.

    The four properties shown in figure 3.1.4

    The four taxonomy questions, the property each one tests, and the name of the resulting class
    Question If yes, the graph is What the panel shows
    Can an edge join a node to itself?a graph with loopsa circle leaving and returning to the left node
    Can two nodes be joined more than once?a multigraphtwo separate curves between the same pair
    Does each edge carry a number?a weighted graphedges labelled 3 and 5

    Definition

    Simple graph
    A graph with no loops, no multiple edges and no edge weights, and which is not directed. Two distinct nodes are joined by at most one edge, and because edges have no direction the edge can be written as a set: {A,B} and {B,A} are the same edge.

    SIMPLE is a simple graph. Königsberg is not — it is a multigraph, because two of its landmass pairs are joined twice. The 10-city graph of group 3.5 is a weighted simple graph.

    3.1.5 Degree of a node

    # Permalink to topic 3.1.5, Degree of a node
    • ● Slides
    • ▣ Lab 07
    • ● Tutorial

    The degree of a node is the number of edges that begin there. It is the simplest useful number you can extract from a graph, and every representation gives you a different way to read it off.

    Degree

    deg(v) = | { e ∈ E : v ∈ e } |

    v
    the node whose degree you want
    E
    the set of edges of the graph
    e
    one edge, counted once for each time it touches v, so a loop adds 2

    How to read a degree from each representation

    Reading the degree of a node from each of the four representations, and what that costs
    Representation Procedure Work for one node
    Edge listLook at every edge and count how many times the node occursproportional to M, the number of edges
    Adjacency matrixFind the row or column for the node and count the onesproportional to N, the number of nodes
    Adjacency structureCount the entries in the node's sublistproportional to the degree itself
    Incidence matrixFind the column for the node and count the onesproportional to M

    Note

    Every edge contributes 2 to the total of all degrees, once at each end. So the degrees of any graph sum to exactly twice the number of edges — a one-line check on any edge list you have just typed in, and the check Lab 07's read_graph is really testing. For SIMPLE: 2 + 2 + 3 + 1 + 0 = 8 = 2 × 4.

    3.1.6 Eulerian paths

    # Permalink to topic 3.1.6, Eulerian paths
    • ● Slides
    • ◐ Tutorial, partial
    • ✚ New for 2026

    An Eulerian path uses every edge of the graph exactly once. It answers both Königsberg and the childhood puzzle "can you draw this without lifting your pen or going over a line twice?" — they are the same question.

    Key idea

    Identify the vertices; count the edges at each one; ignore every vertex with an even count; let c be the number of vertices left. If c = 0 or c = 2 the figure can be drawn, and otherwise it cannot. When c = 2 you must start at one odd vertex and finish at the other.

    The reason is a counting argument, not a search: every visit to a vertex uses one edge going in and one coming out, so an odd vertex can only be a start or a finish, and a single stroke has only one of each.

    3.2 Representation

    3.2.1 Edge list

    # Permalink to topic 3.2.1, Edge list
    • ● Slides
    • ▣ Lab 07
    • ● Tutorial

    The simplest representation there is: write down each of the M edges as its pair of vertices. For SIMPLE that is {{A, B}, {A, C}, {B, C}, {C, D}}, usually shortened to {AB, AC, BC, CD}.

    Four questions the slides ask about it, and the answers:

    The four discussion questions about the edge list, answered

    The edge-list discussion questions from the slides, with the answers the slides leave to the class
    QuestionAnswer
    Does it adequately represent the graph?Almost. It records every edge exactly.
    What is missing?Node E. An edge list can only name nodes that appear in an edge, so isolated vertices vanish.
    How could we improve it?Ship the node count, or a separate node list, alongside the edges — which is what the GRF format and every real file format do.
    Are there graphs for which it is not useful?Dense graphs, where M approaches N squared, and any task that asks "are these two nodes adjacent?" repeatedly, since answering needs a scan of the whole list.

    Common mistake

    Reading the number of nodes off the edge list. SIMPLE's edge list mentions A, B, C and D, so a program that infers N from the list will say 4 and silently lose E. Lab 07's read_graph asks you to return n_nodes separately for exactly this reason.

    3.2.2 Storing an edge list

    # Permalink to topic 3.2.2, Storing an edge list

    People want labels — 'A', 'B', 'C', or 'Pittsburgh', 'Cincinnati'. Computers want numeric indices, because an index can be used to subscript an array. So store the edges as index pairs and keep the labels in a second array you look up when printing.

    Python SIMPLE as an edge list of numeric indices 
    EdgeList = [
    [1, 2],
    [1, 3],
    [2, 3],
    [3, 4] ]

labels = ['A', 'B', 'C', 'D', 'E']   # index 1 is 'A'; keep it separate
n_nodes = len(labels)                # 5 — NOT inferred from EdgeList

    Lab 07 stores the same thing in a text file, one edge per line, as 0, 1 — comma and space. np.loadtxt(fname, delimiter=',') handles it; a hand-rolled line.split(',') leaves you with the string ' 1' and needs a .strip().

    Note

    Whether indices start at 0 or 1 is a decision you have to make once and write down. The slides index from 1 (A is node 1); Python indexes from 0; Lab 07's files index from 0. Most graph bugs in this course are an off-by-one between those conventions.

    3.2.3 Adjacency matrix

    # Permalink to topic 3.2.3, Adjacency matrix
    • ● Slides
    • ▣ Lab 07
    • ● Tutorial
    • ★ Midterm

    For N vertices, the adjacency matrix A is N × N, and entry (i, j) says whether vertex i and vertex j are joined.

    Adjacency matrix

    Ai,j = 1 if vertices i and j are connected; 0 otherwise

    i, j
    vertex indices, 1 to N
    Ai,i
    0 for a simple graph, because a simple graph has no loops

    The adjacency matrix of SIMPLE

    Adjacency matrix of SIMPLE, node order A, B, C, D, E. Twenty-five entries hold the same four edges the edge list held in four.
    Row node A B C D E
    A01100
    B10100
    C11010
    D00100
    E00000

    Three things to take from that table. It is symmetric, because in an undirected graph "A joins B" and "B joins A" are the same fact — which is what the tutorial's self-check question is asking. It is sparse: 8 of its 25 entries are non-zero, and real graphs are far sparser still, which is the whole argument for the adjacency structure of 3.2.4. And unlike the edge list it does record node E, as a row and column of zeros.

    Note

    Reorder the vertices and you get a different matrix for the same graph. Deciding whether two matrices describe the same graph is the graph isomorphism problem, and no efficient general algorithm for it is known. Disproving isomorphism is easier: matrices of isomorphic graphs share their eigenvalues, so they must also share their trace and determinant.

    Make a list of sublists. The sublist for each node names all the vertices adjacent to it, so its length varies from node to node — it is exactly the degree.

    The adjacency structure of SIMPLE

    Adjacency structure of SIMPLE, written the way the slides write it. Node 5 (E) has an empty sublist, so unlike the edge list this representation keeps it.
    Node Sublist Length of the sublist
    1 (A)2, 32
    2 (B)1, 32

    Python Building the adjacency structure from an edge list 
    adj = {label: [] for label in labels}      # every node, including isolated ones
for u, v in edges:
    adj[u].append(v)
    adj[v].append(u)                      # undirected: record it at both ends

for node in labels:
    adj[node].sort()                      # a fixed order makes traces reproducible

    Sorting each sublist is not required by the definition, but it is required if you want a depth-first search to produce the same trace twice. Every trace on this page sorts neighbours alphabetically for that reason.

    3.2.5 Incidence matrix

    # Permalink to topic 3.2.5, Incidence matrix
    • ● Slides
    • ◐ Tutorial, partial
    • ✚ New for 2026

    The incidence matrix is the only representation that carries information about both vertices and edges, because it gives every edge a number of its own. With N vertices and M numbered edges it is M × N: rows describe edges, columns describe vertices.

    The incidence matrix of SIMPLE

    Incidence matrix of SIMPLE: four edge rows by five node columns. Every row has exactly two ones, because every edge touches exactly two nodes.
    Edge A B C D E
    AB11000
    AC10100
    BC01100
    CD00110

    Read a row and you get the two vertices that edge joins. Read a column and you get every edge that touches that node, so the number of ones in a column is the node's degree — and the all-zero column for E is again where the isolated node shows up.

    Common mistake

    Many textbooks write the incidence matrix the other way round, as N rows of vertices by M columns of edges. This course uses edges-as-rows, following the slides. Say which convention you are using whenever you hand one in; the two are transposes of each other and neither is wrong.

    i  x  y  n1 n2 … nk

    x, y

    n1 … nk

    3.2.7 Space and time trade-offs between representations

    # Permalink to topic 3.2.7, Space and time trade-offs between representations
    • ◐ Slides, partial
    • ● Tutorial

    All five representations hold the same graph. They differ in how much room they take and in which question they answer quickly, and that is the only basis on which to choose between them.

    Space and time costs of the five representations

    Cost of each representation, with N nodes and M edges. "Is u next to v?" and "list the neighbours of u" are the two questions every graph algorithm asks.
    Representation Space Is u next to v? List the neighbours of u Keeps isolated nodes?
    Edge list2MO(M) — scan every edgeO(M) — scan every edgeNo
    Adjacency matrixN²O(1) — one lookupO(N) — scan a rowYes
    Adjacency structureN + 2MO(deg u)O(deg u) — the best possibleYes
    Incidence matrixM × NO(M)O(M)Yes
    GRF fileN + 2M + 2N coordinatesO(deg u)O(deg u)Yes

    Key idea

    Choose by density. A sparse graph — M much smaller than N² — wants the adjacency structure. A dense graph, or code that constantly asks "is u next to v?", wants the matrix. Real networks are almost always sparse, which is why the adjacency structure is the usual default.

    3.3 Connectivity

    3.3.1 Connectivity of a graph

    # Permalink to topic 3.3.1, Connectivity of a graph
    • ● Slides
    • ▣ Lab 07
    • ● Tutorial

    An edge list only ever reports pairs that are directly connected. Edges carry local information. Drawing the graph reveals something the edge list never states: the big picture, the global information.

    The most important global property is connectivity. Three questions follow from it, and the rest of this group is about turning local edge data into answers to them:

    1. Can we travel from node A to node Z at all?
    2. Can we travel from any node to any other node?
    3. What is the quickest way from A to Z?

    Key idea

    Every algorithm in this group and the next is a machine for turning local information into global knowledge. That is the whole job. Once you see it that way, the connection algorithm, depth-first search and Dijkstra all look like the same shape of thing: start somewhere, repeatedly follow edges you have not followed, and keep a record of what you have learned.

    3.3.3 Adjacent nodes, simple graphs

    # Permalink to topic 3.3.3, Adjacent nodes, simple graphs
    • ● Slides
    • ● Tutorial

    Two nodes are adjacent when a single edge joins them — they are directly touching. Adjacency is the atom: every longer relationship in this module is built by chaining adjacencies together.

    In a simple graph — no loops, no multiple edges, no weights, not directed — two distinct nodes either are joined by exactly one edge or are not joined at all. That is what lets you write an edge as a set: {A, B} and {B, A} name the same edge, and it is what makes the adjacency matrix symmetric with zeros down its diagonal.

    Common mistake

    Treating "adjacent" and "connected" as synonyms. In SIMPLE, A and D are connected — the path A–C–D joins them — but they are not adjacent, because no single edge does. The adjacency matrix answers adjacency in one lookup; answering connectivity needs an algorithm.

    3.3.4 Walks and paths

    # Permalink to topic 3.3.4, Walks and paths
    • ● Slides
    • ● Tutorial

    Reaching a non-adjacent node means travelling through a series of adjacent ones. There are two equally good ways to write down that journey: as a node list in visit order, (A, B, E, C), or as an edge list in use order, (AB, BE, EC). Each consecutive pair of edges must share a node, because one edge got you there and the next takes you away.

    Definition

    Walk from A to B
    A node list whose first element is A, whose last element is B, and in which every consecutive pair of nodes is adjacent.
    Path
    A walk in which no edge is used more than once.
    Cycle
    A path that begins and ends at the same node.

    On SIMPLE, A–C–B–A–C–D is a walk from A to D but not a path, because the edge AC is used twice. There are exactly two paths from A to D: A–B–C–D and A–C–D. Paths turn out to be much more interesting than walks — and much harder to count, which is the point of 3.3.10.

    Note

    The tutorial defines a path as a walk that repeats no vertex, while the slides define it as a walk that repeats no edge. On every example in this module the two definitions agree. The vertex version is the one used for shortest paths in 3.5.4, because a shortest path never revisits a node, and it is the one the demos here enumerate.

    3.3.6 The connection algorithm

    # Permalink to topic 3.3.6, The connection algorithm
    • ● Slides
    • ▣ Lab 07
    • ◐ Tutorial, partial
    • ✚ New for 2026

    Given the edge list and two node indices A and B, is there a path? The connection algorithm answers it by keeping every node in exactly one of three sets: used (already explored), new (discovered but not yet explored) and untouched (not yet discovered).

    Pseudocode The connection algorithm 
    used      = {}
new       = {A}
untouched = {all nodes but A}

1. If new is empty, we failed. Exit.
2. Move one item from new into used; call it S.
3. For each edge which uses S:
       label the other node in the edge T
       if T equals B          -> we succeeded, exit
       else if T is untouched -> move T into new
4. Go back to step 1.

    The three sets are usually stored as three bit vectors of length N, where entry T is 1 when node T is in that set. A node belongs to exactly one set at a time, so setting one entry means clearing the other two.

    3.3.7 Connected components

    # Permalink to topic 3.3.7, Connected components
    • ● Slides
    • ▣ Lab 07
    • ● Tutorial

    The connection algorithm "fails" when there is no path, and it notices by running out of nodes in new. That failure is the most useful thing it does: it means the graph has at least two components, and repeated failures count them exactly.

    Delete the line "if you reach B, you have succeeded" and the algorithm no longer stops early. It runs until every node reachable from the start has been moved into used — and that set of used nodes is precisely one connected component. Wrap that in an outer loop and you have the component algorithm:

    Pseudocode The connected component algorithm 
    1. Initialize used and new to {}
2. Initialize untouched to include all nodes
3. Set the component count c = 0, then loop:
     i.   if untouched is empty, successful exit
     ii.  move one node from untouched to new
     iii. c = c + 1
     iv.  call the MODIFIED connection algorithm
     v.   go back to (i)

    At the end, c is the number of connected components, and the modified algorithm has also recorded which component each node belongs to. On DISCONNECTED it returns c = 3, with components {A, D, E, F}, {B, C, H} and {G}. Switch on component mode in the demo at 3.3.6 to watch it happen.

    Note

    An isolated node is a component of its own, containing one node and no edges. Programs that build the component list from the edge list alone always undercount for exactly this reason — the same defect as topic 3.2.1, arriving one layer later.

    3.3.8 Modified connection algorithm

    # Permalink to topic 3.3.8, Modified connection algorithm
    • ● Slides
    • ▣ Lab 07

    The inner loop called by the component algorithm. It assumes c and the three sets have already been set up, and it differs from the original in exactly two places.

    Pseudocode The modified connection algorithm 
    1. If new is empty, exit.                     <- exit, without admitting failure
2. Remove one item from new; call it S.
3. For each edge which uses S:
       call the other node T
       if T was untouched -> move it into new  <- no early exit on reaching B
4. component(S) = c
5. Move S into used.
6. Go back to step 1.

    3.3.10 Counting paths

    # Permalink to topic 3.3.10, Counting paths
    • ● Slides
    • ● Tutorial
    • ✚ New for 2026

    Keep multiplying and the entries of Ak keep growing. On a ten-node graph, discovering that there are several thousand hundred-step walks between two nodes is not difficult, not interesting, and almost never useful. What you usually want is the number of paths.

    Paths are harder, and the reason is structural: the matrix trick works precisely because it does not care where you have been, and "no repeats" is a statement about where you have been. There is no matrix power that counts paths.

    Key idea

    What you get instead is a guarantee that the search terminates. A path may not repeat a node, so it can use at most N − 1 edges. Any procedure that extends partial paths one node at a time therefore stops after at most N − 1 rounds — which is exactly what makes the depth-first path generator of 3.4.4 a finite algorithm rather than an infinite one.

    3.4 Traversal

    3.4.1 Depth-First Search: concept

    # Permalink to topic 3.4.1, Depth-First Search: concept
    • ● Slides
    • ● Tutorial

    We need a way to visit every node of a graph. Depth-first search does it by following one branch of possibilities all the way to its end, while remembering all the other possibilities to examine later.

    The slides frame it as visiting a museum: eighteen rooms, walls between some of them, and you enter at room Q. Go as far as you can into new territory; when you hit a dead end, back up to the last room you had not finished exploring. Perfect memory is the only thing the method needs — and the data structure that provides it is a stack, a list of unfinished work where the last item placed on is the first taken off.

    Definition

    Stack
    A list of unfinished work in which the last item placed on is the first taken off — last in, first out, or LIFO. Recursion uses one implicitly; this course uses an explicit one so you can print it.
    Depth-first search
    A traversal that repeatedly moves to an unvisited neighbour of the current node, pushing the rest onto the stack, and backs up by popping the stack when no unvisited neighbour remains.

    One consequence worth noticing early: the edges the search actually uses form a spanning tree of the graph. Keep only those and you have just enough edges to hold the graph together — the object group 3.6 is about.

    3.4.2 DFS: the algorithm in words

    # Permalink to topic 3.4.2, DFS: the algorithm in words
    • ● Slides
    • ● Tutorial

    Choose a starting node. It has neighbours and you must visit them all, one at a time — so pick one, move there, and remember the others by putting them on the stack.

    The new node has neighbours too, one of which is the node you just came from. You do not want to go back, so you must remember which nodes you have already visited. Look at the unvisited neighbours of this node, pick one, put the rest on the stack, and keep going until you reach a node with no unvisited neighbours.

    You have now gone to maximum depth on this path. What next? Take the next node off the stack. It may have been visited since it was put there, so keep drawing until you find an unvisited one, then start wandering again. If the stack empties and you know the graph is connected, you are done. If it is not connected — or if you do not know — look for any unvisited node and restart the whole algorithm from there.

    Key idea

    After initialisation the algorithm repeats exactly two tasks: put things on the stack, and take things off the stack. Everything else is bookkeeping. If your implementation is doing a third thing, it has probably grown a bug.

    3.4.5 Breadth-First Search

    # Permalink to topic 3.4.5, Breadth-First Search
    • ◐ Slides, one line
    • ● Tutorial

    The related method. Start at a given node, visit every node exactly one edge away, then every unvisited node two edges away, and so on. Where depth-first search is a person walking a maze, breadth-first search is a stone dropped in a pond: expanding concentric rings.

    The code is the depth-first code with one substitution. Replace the stack with a queue — first in, first out — and everything else stays the same.

    Python Breadth-first search, with the distance in edges 
    from collections import deque

def bfs(adj, start):
    visited = {start}
    dist    = {start: 0}
    order   = []
    queue   = deque([start])

    while queue:
        cur = queue.popleft()          # FIRST in, first out — the only difference
        order.append(cur)
        for nb in adj[cur]:
            if nb not in visited:
                visited.add(nb)
                dist[nb] = dist[cur] + 1
                queue.append(nb)
    return order, dist

    Key idea

    On an unweighted graph, breadth-first search finds the shortest path in number of edges, and depth-first search does not. The reason is the order: BFS finishes every node at distance k before it touches any node at distance k + 1, so the first time it reaches a node is by a shortest route. Weight the edges and this stops being true, which is where Dijkstra comes in.

    The traversal demo at 3.4.1 runs both algorithms on the same graph from the same start, and its table reports the distance in edges from the start for every node it visits.

    3.5.5 Dijkstra's algorithm

    # Permalink to topic 3.5.5, Dijkstra's algorithm
    • ● Slides
    • ● Tutorial
    • ★ Midterm

    Edsger Dijkstra's answer to the same question, designed to be simple to program, efficient to run and provably correct. It never generates a path at all. Instead it keeps three things: which nodes have been connected so far, the shortest distance from A explored so far for every node (Dist), and the current node P.

    Pseudocode Dijkstra's algorithm, single target 
    1. For all nodes X: Dist(X) = infinity, CONNECT(X) = 0.
   Then P = A and Dist(A) = 0.
2. Connect node P:  CONNECT(P) = 1.
3. For every unconnected node X with a finite edge (X,P):
       Dist(X) = min ( Dist(X), Dist(P) + Length(X,P) )
4. If no unconnected node has a finite Dist, we are done:
   there is no path to B.
5. Set P to the CLOSEST unconnected node — the one with the
   smallest Dist.
6. If P is B, we are done, and Dist(B) is the shortest distance.
7. Go to step 2.

    Step 3 is the heart of it and has a name of its own:

    Relaxation step

    Dist(X) ← min ( Dist(X), Dist(P) + Length(X, P) )

    P
    the node just connected
    X
    a neighbour of P that is not yet connected
    Length(X, P)
    the weight of the edge between them, from the edge-length matrix
    Dist(X)
    the best distance to X found so far

    Key idea

    Once a node is connected, its Dist never changes again. That is what makes the algorithm fast, and it is true for a reason: any alternative route to P would have to leave through some other unconnected node Q, and Q's Dist is at least P's Dist because P was chosen as the smallest. Adding more non-negative edges to something already at least as large cannot make it smaller.

    Common mistake

    Running Dijkstra on a graph with a negative edge weight. The correctness argument above uses "non-negative" in its last sentence, and without it the greedy choice is simply wrong: a later negative edge can reduce a distance that has already been fixed. If you need negative weights, you need a different algorithm.

    Python Dijkstra with a predecessor array, so the route can be printed 
    import math

def dijkstra(adj, source):
    dist = {v: math.inf for v in adj}
    prev = {v: None for v in adj}
    connected = set()
    dist[source] = 0

    while len(connected) < len(adj):
        # step 5: the closest unconnected node. Linear scan; a heap is faster.
        p = min((v for v in adj if v not in connected), key=lambda v: dist[v], default=None)
        if p is None or dist[p] == math.inf:
            break                                  # step 4: nothing reachable left
        connected.add(p)                           # step 2

        for x, w in adj[p]:                        # step 3: relax
            if x not in connected and dist[p] + w < dist[x]:
                dist[x] = dist[p] + w
                prev[x] = p                        # remember HOW we got there
    return dist, prev

    Note

    The prev array is not in the slide version and was missing from the 2025 dashboard, which is why that dashboard could report a distance but never a route. It costs one assignment per relaxation. Without it you cannot answer "which way do I actually go?", and the midterm asks exactly that.

    3.5.9 Algorithm classification (greedy)

    # Permalink to topic 3.5.9, Algorithm classification (greedy)
    • ● Slides
    • ● Tutorial

    Dijkstra's algorithm is a greedy algorithm. At each step it simply takes the edge that looks best — the shortest — with no regard for long-term strategy. The only checks it makes are that the new edge joins an already-connected node to a new one, and that it has the lowest distance among all such edges.

    The advantage of a greedy algorithm is that the decision process is simple and efficient. The danger is that greedy is usually wrong: taking the locally best option does not generally produce the globally best result. Dijkstra is one of the cases where it does, and the non-negative-weight condition is exactly the price of that guarantee.

    3.6.5 Cycle detection / Union-Find

    # Permalink to topic 3.6.5, Cycle detection / Union-Find
    • ● Slides
    • ▣ Lab 08
    • ● Tutorial

    Step 3 of Kruskal hides the only hard part: how do you check whether edge E(i) adds a cycle to T?

    The slides give a test that works while the tree is being built: E(i) is a pair {A, B}, and it adds a cycle if and only if both A and B already occur somewhere in T. At step 7 of the worked example, T was {{A,B}, {A,F}, {D,I}, {E,F}, {E,G}, {E,H}} and the edge under consideration was {F, G}. Both F and G already appear, so it was rejected and the algorithm moved on to the next longest edge, {C, D}. Why was {C, D} acceptable? Because neither C nor D appeared in T at all.

    Key idea

    The real question is "are A and B already in the same piece?", and the data structure that answers it is union-find, also called a disjoint-set union. find(v) returns an identifier for the piece v is in, and union(u, v) merges two pieces. Equal finds means same piece means cycle, so discard; different finds means add the edge and union.

    Python Union-find with path compression and union by rank 
    class UnionFind:
    def __init__(self, nodes):
        self.parent = {v: v for v in nodes}
        self.rank   = {v: 0 for v in nodes}

    def find(self, v):
        while self.parent[v] != v:
            self.parent[v] = self.parent[self.parent[v]]   # path compression
            v = self.parent[v]
        return v

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                                   # same piece: a cycle
        if self.rank[ra] < self.rank[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra                               # union by rank
        if self.rank[ra] == self.rank[rb]:
            self.rank[ra] += 1
        return True

def kruskal(graph):                # graph is a list of (u, v, w)
    uf = UnionFind({v for u, v, w in graph for v in (u, v)})
    mst, total = [], 0
    for u, v, w in sorted(graph, key=lambda e: e[2]):
        if uf.union(u, v):
            mst.append((u, v, w))
            total += w
    return mst, total

    Common mistake

    Implementing "same piece?" by keeping a Python set per node and comparing set objects. It gives the right answer, but merging two pieces then costs O(n) because every member has to be updated — which is what the 2025 dashboard did while its comment claimed union-find. With path compression and union by rank each find is very nearly constant time, and the parent array is also something you can print and check in a trace.

    The Kruskal demo at 3.6.4 shows the two set identifiers returned by find for each edge it considers, so you can see the exact comparison that produced "added" or "rejected".

    3.6.9 Random permutation generation

    # Permalink to topic 3.6.9, Random permutation generation
    • ● Slides
    • ✚ New for 2026

    The sampling task. Fisher and Yates' shuffle produces a uniformly random permutation in N − 1 swaps, which is as cheap as it could possibly be.

    Pseudocode Random permutation of order N 
    Initialize P to [ 1, 2, ..., N ];

for I = N down to 2
  choose a random integer J between 1 and I;
  swap P(I) and P(J);
end

    Key idea

    J is drawn from 1 to I, not from 1 to N. That is the whole algorithm. Position I is being finalised on this pass, so its occupant is chosen from everything not yet finalised — which is what makes all N! outcomes equally likely. Drawing J from 1 to N instead produces a shuffle that is measurably biased, and it is the classic way to get this wrong.

    # Permalink to topic 3.6.10, The next-permutation algorithm

    The generation task: given one permutation, produce the next one in the list, using no memory beyond the permutation itself. Harder to describe than the shuffle, but it is what lets a brute-force solver walk through all N! itineraries without ever storing more than one.

    1. Initialize. If P is all zeros, return with P = 1:N.
    2. Seek I, the highest index for which P(I) < P(I+1).
    3. If no such I exists, the current permutation is the last one. End.
    4. Seek J, the highest index so that P(I) < P(J).
    5. Interchange P(I) and P(J).
    6. Reverse the order of P(I+1 : N) and return to step 2.

    • ✚ New for 2026

    Given N cities and their pairwise distances: initialise R* = [ ] and D* = ∞; then, while more routes are available, generate the next route R, measure its length D, and if D < D* update both. At the end R* is the best possible route and D* is its length. The "generate the next route" step is next_perm from 3.6.10.

    Key idea

    There are 5! = 120 permutations of five cities, but only 12 genuinely different round trips. Every tour appears 10 times: 5 rotations (the same loop entered at a different city) times 2 directions. The slides write it out — ABCDE = BCDEA = CDEAB = DEABC = EABCD = AEDCB = BAEDC = CBAED = DCBAE = EDCBA = 25 — and 120 ÷ 10 = 12.

    The optimum for the 5-city example is ACBED, at 4 + 4 + 3 + 6 + 2 = 19. The last term is the return leg from D back to A: forgetting it is the single most common error in a TSP implementation, because the cost of a tour is cyclic and a naive loop over the permutation only adds N − 1 of the N legs.

    Python Brute-force TSP solver, with the return leg 
    import math
from itertools import permutations

def tsp_brute_force(dist, cities):
    start  = cities[0]                              # fixing the start removes N rotations
    others = cities[1:]
    best_d, best_r = math.inf, None

    for rest in permutations(others):
        route = (start,) + rest
        d = sum(dist[route[i]][route[(i + 1) % len(route)]]
                for i in range(len(route)))         # % closes the cycle: D back to A
        if d < best_d:
            best_d, best_r = d, route
    return best_r, best_d

    Common mistake

    Believing brute force scales. "How many itineraries are possible with 48 cities?" 48! is about 1.24 × 1061, or about 1.29 × 1059 genuinely distinct tours. A machine testing 1012 tours per second would need far longer than the age of the universe. And yet good solutions have been found for problems with as many as 85,000 cities — by not using brute force.

    3.6.13 TSP heuristics

    # Permalink to topic 3.6.13, TSP heuristics
    • ● Slides
    • ✚ New for 2026

    Definition

    Heuristic
    A method for making a good guess, or for improving a random guess. It offers no guarantee of optimality, and in exchange it finishes.

    The nearest-neighbour heuristic for the TSP: pick a starting point at random, then build an itinerary by moving from your current location to the nearest unvisited city, again and again, until you must return home. Generate many itineraries this way and keep the shortest.

    "We never found the optimal route of 19, but we did OK" — 21 against 19 is a 10.5 per cent excess, for five tours built instead of 120 evaluated. Notice the shape of the failure: the heuristic takes the cheap hops early and is left with an expensive leg home, which is exactly what greed does when there is no proof behind it.

    Note

    The slides ask: if you are prepared to compute up to 100 itineraries, what is different about problems of 50, 150 and 10,000 nodes? At 50 cities you can start from every city twice over and still be under budget. At 150 you cannot even start from every city once, so the choice of starting points itself becomes a design decision. At 10,000 you sample a hundred starts out of ten thousand — one per cent — and the heuristic's quality now rests entirely on how good a single nearest-neighbour pass is.

    3.6.14 Improving a good route (local search)

    # Permalink to topic 3.6.14, Improving a good route (local search)
    • ● Slides
    • ✚ New for 2026

    Once you have a route, you can often improve it without starting again. The key observation needs one assumption: that the intercity distances are "real" distances, obeying the triangle inequality.

    Triangle inequality

    d(A, C) ≤ d(A, B) + d(B, C)

    d(A, C)
    the direct distance from A to C
    meaning
    a detour through B is never shorter than going straight

    Key idea

    If a good route crosses itself — the leg from A to B and the leg from C to D cross over each other — then a better route always exists: go from A to C and from B to D instead, reversing the stretch in between. This is the 2-opt move, and repeating it until no crossing remains is the simplest useful local search.

    On the 5-city example, the nearest-neighbour route from A is A-D-C-B-E-A at 21 units. One 2-opt move fixes it: reverse the stretch C-B-E to get A-D-E-B-C-A, which measures 2 + 6 + 3 + 4 + 4 = 19 — the optimum, found without evaluating a single one of the other 118 permutations.

    Common mistake

    Assuming a 2-optimal route is optimal. "No single reversal improves this route" is a much weaker statement than "no route is shorter". Local search finds a local minimum and stops; whether that is the global minimum is exactly what it cannot tell you. On this 5-city example it happens to be — start the demo from a different city and it often is not.
